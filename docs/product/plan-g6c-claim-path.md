# Plan: the claim path for run records (G6c, task #62)

Status: **plan, awaiting owner review** (written 2026-10-15). Branch `feat/claim-path`, stacked on `feat/ice-field-cabinet`. It
turns the G6 spike (a run record and a replay verifier that nothing calls) into something a player's milestone can use,
**without tying the platform to any game**.

## 1. The principle (owner, 2026-10-15)

- **The platform exposes a few generic APIs and contains no game logic.** A third-party game must onboard without a platform
  release, a platform pull request or platform code that names it.
- **Every game is client-only and calls only our API.** A game has no backend of its own, so it cannot attest its own results
  and cannot hold secrets. Anything a game needs from a server, the platform provides, generically.
- A game **declares in its manifest** how each of its milestones can be trusted, and the platform provides the matching
  generic mechanism.

### What this changes in what was built

The G6 spike registers FROST·BITE's rules by importing them into the platform (`configs/verifiers.ts` imports
`@game/frostbite`; the web app and the repository root depend on it). That is the platform tied to one game, and it would not
work for an outside builder. This plan **replaces that registry** with verifiers loaded from each game's own build output.
FROST·BITE becomes one game using the interface, with no special place in the platform.

## 2. Trust levels a game can declare, per milestone

| Level                            | What the platform does                                                                                       | What it proves                                                                                                                            | Status                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `self-reported` (default)        | Nothing.                                                                                                     | Nothing. The game said so.                                                                                                                | Built.                                        |
| `replay-verified`                | Replays the game's own **published rules** on the server, from a platform-issued seed, and checks the claim. | The recorded inputs were **legal under the game's rules** and reach the result. Not that a human played, and not that the rules are fair. | **This plan.**                                |
| (later) replay with a **dealer** | As above, but hidden information (shuffled cards, mine positions) is held by the platform, not the browser.  | As above, plus the player could not have read the answer.                                                                                 | **New task G6e**, not built here (section 9). |

**Not supported:** attestation by a game's own server. Games are client-only, so there is no such server. The ADR-018
attestation service (GP-06) is about signing mints, not about trusting a game's results, and is untouched.

**Hidden information is no longer "the game's problem."** A game with hidden information cannot be honestly replay-verified
today (the browser can compute the answer), so it stays `self-reported` until the dealer exists. The platform cannot enforce
that a game's rules have no hidden information (it cannot read intent), so the manifest field is a declaration, the label says
exactly what was checked, and leaderboards (SDK-2) will require the declaration. See risk R2.

## 3. How a game becomes verifiable (all inside the game's own package)

1. **Write the rules as a pure state machine** (`GameVerifier`, already in `@ador/game-sdk/run-record`): `init`, `step`,
   `earned`. The game's UI plays through the same module.
2. **The build emits a verifier artifact** next to the game's bundle: `verifier.js` (the rules plus a one-function wrapper,
   `replay(recordText) -> resultText`, generated by the SDK so the surface is a string in and a string out) and
   `verifier.json` (`{ id, version, sha256, bytes }`). `buildGames` produces both from the game's `src/verifier.ts`.
3. **The manifest declares it**: `verification: { replay: { artifact: "verifier.js", sha256, version } }`, and each milestone
   the rules can decide says `verification: "replay-verified"` (default `self-reported`). **The platform accepts a verified
   milestone only if the manifest declares it replay-verifiable**, so a verifier cannot grant an arbitrary id.
4. **The game starts and submits runs through the SDK** (section 5), never touching the network itself.

No platform file changes for a new game. `pnpm game:new` is extended later to scaffold the rules module (not in this task).

## 4. The platform side (generic, no game names)

### 4.1 The artifact runner

A **port**: `VerifierRunner.replay(artifact, recordText) -> ResultText`, with the artifact loaded by digest from the game's
build output and refused if its hash does not match the manifest's.

- **First-party runner (in this task):** runs the artifact in the server process, only for games the repository's own
  configuration marks first-party. It is the same interface as the sandboxed runner, so nothing above it changes.
  It refuses any artifact not marked first-party, so it cannot be used by accident for outside code.
- **Sandboxed runner (separate gated task, with an ADR):** runs outside games' artifacts in an isolated runtime with a time
  and memory limit. `node:vm` is not a security boundary and is not acceptable. Until it exists, **outside games stay
  `self-reported`**; nothing else is lost. This is stated in the manifest validation, not left to review.

### 4.2 The run lifecycle (server-issued seeds, single use)

States: `issued` -> `submitted` (with a verdict) or `expired`. Per run: id, player, game, game version and **verifier digest at
issue** (so a later release cannot change what the run is checked against), the seed (random 32 bits from the server), issue and
expiry times.

- **Start**: a signed-in player asks for a run for a game; the platform issues a run. A signed-out player is told runs are
  unavailable and the game carries on `self-reported` (the account is where a verified level is stored).
- **Submit**: the record must carry the issued seed, the game's id and the digest-pinned verifier version; the run must be
  `issued` and not expired; the transition `issued -> submitted` is one atomic update, so a record is accepted **once**.
  A second submission, an expired run, another player's run, or a mismatched seed are refused.
- **Limits** (typed policy): run lifetime (default 24 hours), open runs per player per game (default 3), starts and submits
  per minute, record size (the SDK's 64 KB ceiling, checked before parsing).

### 4.3 Storing the verdict

- A `game_runs` table (migration): the fields above, the verdict (`verified` or `rejected` with the reason), the digest, and
  **the canonical record text** (at most 64 KB) so a result can be audited later. Retention is a typed policy; the default keeps
  verified records and prunes rejected ones after 90 days.
- On `verified`, the milestones the replay earned **that the manifest declares replay-verifiable** are written to the player's
  milestone record with the level `replay-verified` and the run id. A milestone already unlocked as `self-reported` is
  **upgraded** (its unlock time is kept); a verified level is **never downgraded** by a later self-reported sync.
- **Scope in v1:** milestones earned once. Repeatable milestones, counts and targets stay `self-reported` (a run's verdict says
  what one run earned, not a running total).

### 4.4 HTTP

`POST /api/v1/games/{gameId}/runs` (start) and `POST /api/v1/games/{gameId}/runs/{runId}/submit`, authenticated, same-origin,
rate limited, with the existing error envelope. They are generic: the game id selects a manifest, nothing more.

## 5. The SDK and protocol (additive, like every other addition)

- Methods `run.start()` -> `{ runId, seed, expiresAt }` or `{ unavailable: "signed-out" }`, and `run.submit({ runId, record })` ->
  a verdict. Capability `runs`, declared in the manifest. Host rate limits (the policy pattern used for `ui.toast` and
  `wallet.connect`) and a size check before the record is parsed.
- The host forwards both to the HTTP routes with the player's session; the game never sees a cookie or the network.
- A game that does not declare `runs` is refused (`permission_denied`), like `wallet.get`.
- The simulated host and the local backend answer `unavailable`, so a game's tests and a builder's local tool work.

## 6. What the player sees (truthful state)

- The dock labels each milestone: **"Reported by the game"** (self-reported) or **"Replay-checked"** (replay-verified), and the
  copy says what was checked: "this run followed the game's published rules." It never says a human played, and the word
  "verified" is used only for the `replay-verified` level.
- A signed-out player sees runs as unavailable, not a broken feature.

## 7. FROST·BITE adopts it as any game would

Its cabinet asks `run.start()` for a seed when it can (signed in); with a platform seed it submits at the end and the verdict
upgrades `first-win` and `first-glacier`. Signed out, it plays with a local seed as today and stays `self-reported`. Its manifest
declares the verifier artifact and which milestones are replay-verifiable (`first-cashout` is not). Its `configs/verifiers.ts`
registration and the web app's dependency on it are **deleted**.

## 8. Phases (each its own commit on one branch)

1. **Manifest and build**: the `verification` declaration and per-milestone level in the manifest schema; `buildGames` emits
   `verifier.js` and `verifier.json`; the SDK generates the string-in, string-out wrapper; manifest validation refuses a
   replay declaration without a matching artifact digest.
2. **Runner and loader**: the `VerifierRunner` port, the first-party runner, the digest-pinned loader; conformance runs on
   the loaded artifact; **delete the code registry and the web and root dependencies on a game**.
3. **Run lifecycle**: migration, repository, service (issue, submit, expiry, limits) with real-PostgreSQL tests of the atomic
   single use and concurrency.
4. **Milestone integration**: the verification level in the shared sync schemas and game-saves rules (upgrade, never
   downgrade), the HTTP operations, rate limits, typed policy.
5. **SDK and protocol**: `run.start` and `run.submit`, capability `runs`, host limits, client, simulated and local backends.
6. **Player-facing**: dock labels and copy; the page's flow for signed-out players.
7. **FROST·BITE adopts it**; the real-browser test plays in the frame signed in and sees the milestone upgraded; the explorer
   game gains probes for the new methods.
8. **Docs, specification update, task record, findings, mutation proof, gates.**

## 9. Not in this task (each filed as its own task)

- **The sandboxed runner and its ADR** (isolated runtime choice, limits, dependency review). Until it lands, outside games
  stay `self-reported`.
- **The dealer** (G6e): a generic platform service that holds hidden information as sealed random draws a game reveals one at
  a time, so replay can cover games of concealment. Sketch only, in section 10.
- Leaderboards (SDK-2), minting (G7), verification of repeatable or target milestones, aggregating several runs.

## 10. The dealer, in a paragraph (for review, not built)

A client-only game cannot keep a secret, so a hidden-information game needs the platform to hold it. A **generic** way:
the game asks the platform for a **sealed shuffle** (for example 25 cells with 5 marked), then **reveals cell by cell**; the
platform records each reveal, and the run record includes the platform's reveals so replay can check the game's rules against
what the platform actually revealed. It names no game: cards, mines, loot tables and dice are all "draw from a sealed
distribution." It covers hidden information that is randomness; it does not cover secrets that depend on other players or on
game strategy. It is a design for a later plan, written down so G6c does not rule it out (the record format and the run
lifecycle leave room for platform-supplied reveals).

## 11. Tests

Unit and integration (real PostgreSQL): the lifecycle (issue, submit once, concurrent double-submit, expiry, another player's
run, a seed that is not the issued one, the open-run limit), the runner and loader (digest mismatch refused, a first-party
runner refusing an unmarked artifact), the manifest validation, game-saves upgrade-never-downgrade, the protocol methods and
their limits, the dock labels. A **conformance test that onboards a made-up second game** with no platform change (a tiny
counter game built and loaded by the same path), proving the principle. Real-browser: FROST·BITE signed in, plays, submits,
and the dock shows the upgrade; signed out it stays self-reported. Mutation proof on every guard.

## 12. Risks

- **R1: outside code on our server.** Mitigated by the first-party-only runner and the sandbox gate; the manifest refuses a
  replay declaration for a game not marked first-party until the sandbox exists.
- **R2: a game declares replay on a game with peekable hidden information.** The platform cannot detect it. The label states
  what was checked, leaderboards require a declaration of no hidden information, and the dealer (G6e) is the real answer.
- **R3: scripted records.** Replay does not prove a human. Server seeds, single use and rate limits narrow it; the product never
  claims it.
- **R4: replay cost.** A record has at most 5,000 inputs and 64 KB; a verifier is expected to be linear in them; the sandbox
  adds a time limit. The first-party runner has none, which is acceptable only because those verifiers are reviewed.
- **R5: verifier drift.** A run is bound to the artifact digest at issue, so a new release cannot change how an issued run is
  checked.

## 13. Decisions I would take on the defaults (review these)

1. Run lifetime 24 hours; three open runs per player per game; start and submit rate limits like the other write routes.
2. Store the canonical record text (64 KB cap); keep verified records, prune rejected ones after 90 days (typed policy).
3. **Signed-in players only** for a verified level; signed out stays self-reported.
4. **Once-earned milestones only** in v1.
5. **First-party runner now, sandbox later behind an ADR**; outside games stay self-reported until then.
6. **Dealer deferred** to G6e; hidden-information games stay self-reported.
7. A verifier cannot grant a milestone the manifest does not declare replay-verifiable.
